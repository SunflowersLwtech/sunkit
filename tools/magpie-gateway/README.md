# magpie-gateway

A [magpie](https://github.com/yetone/magpie) gateway on llm-gateway (AWS us-east-1, t4g.large). The subscriptions are signed in on the server only, and magpie is not installed on the client machines.

Part of [sunkit](../../README.md). Not a plugin.

## Use it per process, never as the global default

Interactive Claude Code stays on Anthropic directly on every machine, which keeps mesh channels, claude.ai connectors and Remote Control. Start a single process on the gateway when you need a model you can't reach directly, for example when the Claude seats have hit their limits:

```sh
claude-gw                                  # Opus 5.5 through the claude-opus-5-5 group
claude-gw --model zed/claude-sonnet-5-5
claude-gw -p "…" --model grok/grok-4.7
```

`claude-gw` is `claude --settings ~/.claude/magpie-settings.json`. That file outranks the global settings, so this one session is on the gateway and no other session is.

**Why not the global default** (2026-10-24 incident): magpie answers a Claude subscription with a Claude Code process on the server, which shares the conversation only through a run of its own. Three things send a turn to a run that has not seen the conversation: a session that was already running before the switch, a move to another seat when one hits its limit, and a run evicted for idling or by a gateway restart. Each time, magpie tells the whole conversation to a new run as one block of text ("a new Claude Code is told the whole conversation: 1422 messages"). The model then writes tool calls as plain text, reads the server's container as its own environment, and loses the session's structure. Each retelling also writes the whole history to the cache again, up to about 920K tokens for one turn. A brand-new short session works; so does `claude -p`.

So keep interactive sessions that are already running off the gateway. Since the evening of 2026-10-25, by the owner's decision, the Opus, Sonnet and Haiku groups try the three Claude Team seats first (`claude/claude-opus-5-5` and so on). `stays=session` keeps a conversation on the seat that first answered it, so a gateway session is retold only when its seat reaches its cap and it moves to the next seat, once per move. Each seat is capped at 95% of its windows (`magpie provider account-cap claude "<email> · DuoCode" 95`), the threshold seat-guard and the dispatcher use, so the gateway leaves the last 5% to sessions signed in to that seat directly.

## Server

- `compose.yaml` is its own compose project, separate from `/opt/llm-gateway` (the products' LiteLLM). It has `mem_limit 5g`, so it can never take LiteLLM's memory.
- The gateway port 3425 is not opened in the security group, and `MAGPIE_ALLOW_IPS` refuses anything outside Tailscale's ranges before a key is read. Each machine has its own gateway key.
- The web UI on 3430 is bound to 127.0.0.1. Reach it with `ssh -fN -L 127.0.0.1:3430:127.0.0.1:3430 llm-gateway`, then open `http://127.0.0.1:3430/?k=<MAGPIE_WEB_KEY>`.
- `MAGPIE_NO_STATS=1`, not `DO_NOT_TRACK`. Claude Code reads `DO_NOT_TRACK` too, and it turns off Claude Code's feature flags in the runs magpie starts.
- The image is pinned by digest. To upgrade, run `docker pull ghcr.io/yetone/magpie:<version>`, put the new digest in `.env`, then `docker compose up -d`.
- Since 2026-11-01 the gateway runs v0.1.2421 (`ghcr.io/yetone/magpie:0.1.2421@sha256:74772e1d…`) with one binary swapped in, the Usage page's reset line kept for accounts shown in brief (a local image built from the fork `SunflowersLwtech/magpie`; an upgrade carries that commit over or loses the line).
- Claude seats answer in Claude Code's interactive mode, not `claude -p` (upstream v0.1.2266+, on by default): magpie starts `magpie claude-tui-helper`, which runs the real interactive Claude Code in a pseudo-terminal and turns its session transcript back into `-p`'s stream-json. Anthropic counts a `-p` request at about twice an interactive one; the transcript of an interactive run says `"entrypoint":"cli"` on every row (a `-p` run's is `sdk-cli` and keeps no transcript). The switch is `claudePrintMode` in `settings.json`: absent or `false` is the interactive mode, `true` sends every run back to `claude -p` without a restart (the file is read again when it changes). magpie writes the file without a `false` (Go `omitempty`), so `false` written by hand is gone after its next save and `jq .claudePrintMode` reads `null`; that is still the interactive mode.
- A run still goes `-p` for a request with images known only by URL, safeguards, a JSON schema, magpie's client cache marks, a first message over 400 KB, and for 30 minutes after the interactive mode failed to start; the gateway log says why (`claude: this run is -p: …`). The 400 KB bound catches every long session told its whole conversation anew (after a gateway restart, a move to another seat, a run let go): after the 2026-11-01 switch, 15 of the first 20 runs were `-p` for it. New conversations run interactive.
- An interactive run's reply comes as whole messages, not token by token: on 2026-11-01 a 1,408-character reply came as 88 deltas over 3.8 s under `-p` (first text at 8.6 s), and as one delta at 15.0 s in the interactive mode.
- `X-Magpie-Account` pins one seat. Claude Code sends a header's characters as single bytes, so a seat name with `·` must go in `ANTHROPIC_CUSTOM_HEADERS` as its UTF-8 bytes (Python: `name.encode("utf-8").decode("latin-1")`); sent as is, magpie finds no such account and answers 404, which Claude Code shows as "There's an issue with the selected model".

## Routing groups

The group ids are Claude's own model names. A request for `claude-opus-5-5` reaches the group, and Claude Code still recognises the model by name, so its effort levels and context window behave as on Anthropic. Since 2026-10-27 every group has `stays=auto`, magpie's default: a conversation stays with the account or key that answered it while its cache there is worth keeping, and is routed afresh after that. With `stays=session` before, a session that fell to GLM-5 or SWE-2 while the seats were full stayed there for the rest of its life (back: `magpie group set <id> stays=session`).

| group | members, in order |
|---|---|
| `claude-opus-5-5` | `claude/claude-opus-5-5` (the three seats) → `kiro/claude-opus-5.5` → `devin/claude-opus-5-5` |
| `claude-sonnet-5-5` | `claude/claude-sonnet-5-5` → `zed/claude-sonnet-5-5` → `kiro/claude-sonnet-5.5` |
| `claude-haiku-5-5` | `claude/claude-haiku-5-5` → `zed/claude-haiku-5-5` → `kiro/claude-haiku-5.5` → `opencode-go/claude-haiku-5-5` |
| `claude-fable-5-1` | `group/claude-opus-5-5` |
| `frontier` | `zed/gpt-6.1-sol` → `grok/grok-4.7` → `zed/gpt-6-sol` → `trae-global/gpt-6.1-sol` → Kimi K3.1 Pro, GLM-5.3, DeepSeek V4 Pro (WorkBuddy, Trae CN) → `trae-cn/qwen3.8-max` → `workbuddy/minimax-m3` → `trae-cn/Doubao-Seed-2.1-Pro` → the OpenCode Go copies |

Kiro (1000 credits a month) is kept for Opus, so Sonnet goes to Zed first. Since 2026-10-31 the three Claude groups hold Claude alone (the owner, after a night on GLM-5.3: no GLM unless needed): GLM, Grok, Bedrock GLM-5, `frontier` and `always-up` (both hold GLM) are out of them, and `server/glm-guard.py` puts GLM back at the end only while the seats are about to run out (see below). Members are named `provider/model`: a stored group that names magpie's found `auto-*` groups gets them marked "not served". Copilot exposes only `copilot/auto`, and the `claude` provider (the subscription bridge) exposes only Opus, Sonnet and Haiku 5.5 (`magpie provider models claude claude-opus-5-5 claude-sonnet-5-5 claude-haiku-5-5`), never Fable.

Within `claude/*`, magpie picks the seat by its Smart routing (the seat with room that renews soonest). A 429 "usage limit reached", or a seat's reading at its cap, rests that seat and the same request goes to the next seat at once; with all three resting the group moves on to its next member. On its own, magpie reads the two seats Claude Code isn't signed in to only from the answers they give, so their readings could be hours old until a request landed there. Since 2026-10-31 `server/seat-refresh.py` keeps every seat's reading current (see [Seat readings](#seat-readings)). `X-Magpie-Account: <email> · DuoCode` pins a request to one seat for a test.

## Health alerts

`server/fleet-watch.py` runs on the gateway host every 5 minutes (`magpie-fleet-watch.timer`). It reads the day's routing log. A group whose answers to clients in the last 15 minutes hold at least 3 failures, and at least half failures, gets an ntfy saying it is broken (a 499, the client hanging up, isn't a failure), and one more when it recovers. A group with no success for 60 minutes gets one tiny real request ("reply PONG") with its own gateway key, `fleet-watch`, user agent `fleet-watch/1`; two failed probes in a row also count as broken. The groups are busy, so nearly every run sends nothing. The probes go one at a time: with the seats full every group falls to the same paid member, and six probes at once pushed it into 429 on 10-27. The day's probes, tokens and the providers they landed on go into `/var/lib/magpie-fleet-watch/daily.jsonl`. Alerts go through the ntfy relay in `/etc/llm-gateway/ops.env`.

On 10-27, its first evening: down `long-opus` 20:00 and `claude-opus-5-5` 20:06 (68 failures, 57 successes in 15 minutes, every seat at its cap and the fallbacks out of credits), up 20:24 and 20:42. Its 42 probes that day came to 26.7K tokens, 241 of them on the paid GLM-5.

Install: `fleet-watch.py` to `/opt/magpie/monitor/` (root, 700), the key in `/etc/llm-gateway/fleet-watch.key` (600), the two unit files to `/etc/systemd/system`, then `systemctl enable --now magpie-fleet-watch.timer`. Off: `systemctl disable --now magpie-fleet-watch.timer`. Tests: `python3 server/fleet-watch.test.py`.

## Seat readings

magpie v0.1.1689 reads a Claude seat's allowance only when that seat answers a request through magpie (Claude Code's `rate_limit_event`) or when someone presses refresh on its card on the Usage page. Once the reset time it read has passed, it clears that window to "0%" with no reset time until the next reading. A spare seat often answers nothing through magpie for hours while the machines signed in to it directly keep using it, so `magpie accounts` and the web UI showed it at "5h 0%" with no reset time, and routing picked seats from that old reading. On 2026-10-31 at 06:53, weiliu@'s reading dated from 10-30 19:16 and showed 0% with no reset; Anthropic had it at 1%, renewing at 08:50. Seats at their cap had a reset time because they had just answered.

`server/seat-refresh.py` runs on the gateway host every 2 minutes (`magpie-seat-refresh.timer`). It reads the cards magpie already holds (`GET /v1/magpie/quotas/cards`, which asks no vendor) and presses a seat's refresh through the gateway (`POST /v1/magpie/quotas/refresh?provider=claude&user=<seat>`, inside the container, because only 127.0.0.1 counts as local). magpie then runs Claude Code's `/usage` in that seat's own config directory, which calls no model and takes about 2 seconds, and the CLI, the web UI and routing all use the new reading. When it presses refresh:

- Never on a seat at its cap: the 5-hour window at 95% or more with its reset ahead, or the 7-day window at 100% with its reset ahead. Their reset time is already shown, and routing leaves them alone until it passes, so capped seats look and rotate as before.
- When the 5-hour window has no reset time, either because its reset passed or because it was never read: at most every 5 minutes. If the last refresh also came back with no reset time, the seat hasn't been used since its last reset and its window hasn't started, so it waits 15 minutes instead.
- When the reading is older than `SR_STALE` seconds (600 by default), and the seat was not refreshed in the last `SR_UNKNOWN_GAP` seconds (300 by default).

It refreshes at most 4 seats a run, one at a time. Since v0.1.2421 the unit sets both values to 180: in Claude Code's interactive mode an answered turn no longer carries a `rate_limit_event` (only a refused one does), so these refreshes, and the signed-in seat's own `/usage` every 5–15 minutes, are all magpie learns of a seat's use. A busy seat is read about every 3–4 minutes, about 50 `/usage` an hour, so the 95% caps are checked against readings a few minutes old rather than ten. Each refresh writes the seat's reading before and after to `/var/lib/magpie-seat-refresh/log`. `--dry-run` prints what it would refresh and why, and refreshes nothing.

Install: `seat-refresh.py` to `/opt/magpie/monitor/` (root, 700), the two unit files to `/etc/systemd/system`, then `systemctl enable --now magpie-seat-refresh.timer`. Off: `systemctl disable --now magpie-seat-refresh.timer`; magpie goes back to reading a seat only when it answers or is refreshed by hand. Tests: `python3 server/seat-refresh.test.py`.

## GLM overflow guard

`server/glm-guard.py` runs on the gateway host every 5 minutes (`magpie-glm-guard.timer`). It reads every Claude subscription's 5-hour use, reset time and reading time from magpie's cards (`/v1/magpie/quotas/cards` inside the container, kept fresh by seat-refresh; nothing is asked of Anthropic), each seat's cap from `providers.json` (`accountWindowCaps` "5 hours", else `accountCaps`, else 100), and the last 30 minutes of use from `quota-history.json`. An account whose 7-day window is used up counts as having nothing left.

- Open (when closed): every seat has less than 15% left, or at the last 30 minutes' pace what the seats have left before their caps runs out within 30 minutes and before the first seat resets. It runs `magpie provider on zcode` if ZCode is off, then `magpie group set <id> models+=zcode/GLM-5.3` for Opus and Sonnet and `models+=zcode/GLM-5.3-Flash` for Haiku. The groups route in order, so GLM answers only once every Claude member is out. A seat magpie gives no 5-hour reading for (a card with an error and no windows, as magpie v0.1.1689 shows a sign-in gone bad) counts as having nothing left here: a seat magpie can't read usually can't answer either. A seat whose window has passed its reset and not been read again (0%, no reset time) is a reading, and counts as free.
- Which GLM (since 2026-11-01): ZCode has an allowance of its own. On 11-01 at 20:09 the guard added `zcode/GLM-5.3` while ZCode's GLM Coding Max week was used up, so the overflow led nowhere. Each run now reads ZCode's windows: from its card when magpie shows one, else (ZCode off, so magpie shows no card) from the newest point in `quota-history.json`, counting only accounts magpie still reads (an account whose newest point is more than 6 hours older than ZCode's newest is gone) and taking a window past its reset as full again. If both GLM Coding Max windows (`5 hours`, `Weekly`) have 2% or more left, a group gets its Max member (`zcode/GLM-5.3`, Haiku `zcode/GLM-5.3-Flash`). Otherwise it gets the free Start Plan member (`zcode/GLM-5.3-Trial`, Haiku `zcode/GLM-5.3-Flash-Trial`) if that member's own daily bucket (`GLM-5.3-Trial · ZCode Start Plan`, resetting at 23:59 +08) has 2% or more left. If neither has room, the group gets nothing; with nothing for any group the guard adds nothing and doesn't turn ZCode on, and the message says the fallback is empty (兜底已空). A gift row that is only text on the card (a plan to claim in the ZCode app) is no reading. With no ZCode reading at all it adds the Max member as before. While open it picks again every run: Max used up → Trial, Trial used up → nothing (and the other groups get their ZCode members back, as at a close), a reset → back again, adding the new member before taking out the old one; each change to the three groups sends a message. Closing takes out whichever of the Max and Trial members is there.
- Close (when open): a seat read in the last 20 minutes has 50% or more left (it has just reset). The GLM members come out, and ZCode is turned off again only if the guard turned it on. Pace is not looked at here: magpie keeps an active conversation on the member that answered it (`stays=auto`), so while GLM stays in the group the sessions that fell to it stay on it; taking it out sends them back to Claude, and the open rule puts it back 15 minutes later if the pace still calls for it. A seat with no reading time, or one older than 20 minutes, or none at all, never counts as back, so missing readings never close it.
- At least 15 minutes between an open and a close, in both directions. Every run reconciles: while closed, those GLM members (Max and Trial) are taken out of the three groups even if someone added them by hand.
- If the cards or `providers.json` can't be read at all, the run changes nothing. After each change it reads `providers.json` back; a change that didn't land is logged as FAILED and reported once, and the state stays as it was. That includes ZCode being off after the guard's `provider off`: if it is still on, ZCode stays the guard's and the next run turns it off again. Whether ZCode is the guard's to turn off is recorded the moment `provider on` or `provider off` succeeds, so a run that fails halfway (ZCode on, a `group set` failing) still turns ZCode off at the next close or reconcile.
- Only the three `claude-*` groups get ZCode from the guard. `provider on zcode` is global, so before the guard turns ZCode on it takes the ZCode members out of every other group that names one and isn't disabled (on the gateway: `frontier` and `auto-glm-5-3` with `zcode/GLM-5.3`, `auto-glm-5-3-flash` with `zcode/GLM-5.3-Flash`; `always-up` reaches ZCode only through the disabled `zcode` group, which magpie skips), and records where each one was. `models-=` doesn't care whether the provider is on, so this comes first and those groups never see ZCode on. At the close the members go back where they were (`group set <id> models=<the whole list>`) before ZCode is turned off: magpie only adds a member whose provider is on, so for the one or two commands in between those groups could reach ZCode. If ZCode is off by then (someone turned it off), the members wait in the state and go back the next time ZCode is on. When someone else had ZCode on before the guard opened, the other groups were using it already and are left alone. A member the guard can't take out without losing something (a rule, weight, `off` or `pick` on it, a group with `fast` or `match` patterns, or a group of ZCode members only, which magpie won't leave empty) stays, and the log line and the switch message name it. Once ZCode is seen off it is no longer the guard's to turn off, whoever turned it on next.
- Each switch is logged to `/var/lib/magpie-glm-guard/log` and sent over mesh to `feishu-assistant` (else `feishu-assistant-backup`, else the ntfy relay in `/etc/llm-gateway/ops.env`), from a send-only sender `magpie-glm-guard` with its own device token in `/etc/magpie-glm-guard/mesh.env` (600).

Install: `glm-guard.py` to `/opt/magpie/monitor/` (root, 700), `mesh.env` with `MESH_RELAY_URL` and `MESH_TOKEN`, the two unit files to `/etc/systemd/system`, then `systemctl enable --now magpie-glm-guard.timer`. Pause: `touch /etc/magpie-glm-guard/paused` (each run exits without touching anything). Off: `systemctl disable --now magpie-glm-guard.timer`. `glm-guard.py --dry-run` prints what it reads and what it would run. Tests: `python3 server/glm-guard.test.py` (fake cards, relay and magpie on 127.0.0.1).

## Feishu assistant fallback (N150)

The Feishu assistant on N150 is pinned to `provider=magpie`, so a gateway outage took the assistant down with it (the nights of 10-26 and 10-27). Three files keep it reachable:

- `client/gw-fallback.n150.py`, in the container as `/feishu-cc/bin/gw-fallback.py`. Every 5 minutes it sends one tiny request with the assistant's own gateway key, model and address (on a seat about 25 s and 1.7K tokens, about 0.5M seat tokens a day). After a failure it checks every minute. Three failures in a row write the flag `/feishu-cc/gw-fallback/direct`, holding the gateway address, and send an ntfy. When the assistant is idle (its last turn finished and 60 s with nothing new, or 20 minutes into the outage regardless) it ends the claude process still on the gateway, and cc-connect resumes the same session with `--resume` on the next message. Five good checks in a row remove the flag and send an ntfy, and the direct process is ended when idle so the next one is back on the gateway. It never edits `config.toml` or restarts cc-connect or the container. With another provider selected it only checks.
- `client/claude-bypass.n150.sh`, the `cmd` cc-connect starts (`/opt/data/feishu-cc/bin/claude-bypass`). When the flag holds the gateway address the process was given, it drops the gateway variables, so claude goes straight to the seat signed in in the container, a gateway-only model name (`frontier`, `auto/…`) becomes Opus, and `GW_FALLBACK_DIRECT=1` is set.
- `client/gw-fallback.n150.sh`, on the host as `/opt/data/feishu-cc/bin/gw-fallback`, from cron every minute (`* * * * * /opt/data/feishu-cc/bin/gw-fallback >/dev/null 2>&1`). It holds the lock, feeds the container's recent log in for the idle check, and hands the checker's ntfy lines to `/opt/data/sre/notify.sh`. Off: remove the cron line, then delete the flag.

Log `gw-fallback/log`, state `gw-fallback/state.json`; `"drill": true` in the state marks the ntfy titles as a drill until it switches back. Tests: `python3 client/gw-fallback.test.py`.

## Client

```sh
install -m 755 client/magpie-client client/claude-gw client/claude-native ~/.local/bin/
vk run -r "K=个人/magpie 网关 (llm-gateway)/MAGPIE_KEY_<MACHINE>" -- sh -c 'printf %s "$K" | magpie-client setup'
```

- `magpie-client setup` writes `~/.claude/magpie-settings.json` (mode 600): `ANTHROPIC_BASE_URL`, `ANTHROPIC_CUSTOM_HEADERS` (`x-api-key: <gateway key>`), `CLAUDE_CODE_ATTRIBUTION_HEADER=0`, and a `modelPicker` that adds `frontier`, GPT-6.1 Sol, Grok 4.7, Kimi, GLM, DeepSeek, Qwen, MiniMax and Doubao after the built-in rows of `/model`. `magpie-client picker` adds the rows to an existing file. In `/model`, press `s` to switch the session only: Enter also saves the model as the default in `~/.claude/settings.json`, and a plain `claude` session can't use a gateway id. It does not touch the global settings. There is no `ANTHROPIC_AUTH_TOKEN`, so Claude Code keeps its claude.ai sign-in, and mesh channels and claude.ai connectors keep working.
- `claude-gw` adds `--model claude-opus-5-5` unless a model is given. Like the shell's `claude` wrapper, it puts `--channels plugin:mesh@sunkit` last for an interactive session. On Windows, use `client/claude-gw.cmd` with the same settings file in `%USERPROFILE%\.claude`.
- Installed on 2026-10-25 on m4, m2, aws-sin, msi-wsl, MSI (Windows), wrsm, bd and devdesk. Each machine got a reply through the gateway from `claude-gw -p`. N150's Feishu assistant gets the gateway as a second cc-connect provider (`/provider magpie`), with Anthropic kept as the default.
- `magpie-client on` / `off` write the gateway into or out of **the global** `~/.claude/settings.json`. Per the section above, don't. Values a running session already loaded stay until it restarts, so deleting the two keys doesn't take a session off the gateway. Empty strings do, through a hot reload. Empty values in the global file also override a process's own environment, so delete them once every session has restarted.
- The 2026-10-25 fix: the key reaches the writer through the environment. The heredoc is python's stdin, so a piped key was lost, and the old version wrote `x-api-key: ` with an empty key and reported success.
- `claude-native` runs one session straight to Anthropic when the global file points at the gateway.
- `client/cc-compactor.py` (`~/.local/bin/cc-compactor`, config in `~/.config/cc-compactor/config.toml` from `client/cc-compactor.toml`): shrinks a stopped Claude Code session before it is resumed. It reads the session's `.jsonl` and the gateway's seat readings (`GET /v1/magpie/quotas`), scores five actions under a weight profile (`cc-compactor explain` prints the table), and `cc-compactor --session <id> compact` writes a summary into the transcript as Claude Code's own `compact_boundary` + `isCompactSummary` pair, after a backup in `~/.cache/cc-compactor/backups`. The summary is a fixed digest (first request, recent prompts, files touched, commands, errors, `git status`) plus a model's reading of up to 18,000 characters of the middle turns, through the gateway: `claude-haiku-5-5`, then `always-up` (GLM came off on 10-31, while ZCode's week was used up until 11-06); with no model answering it uses the digest alone. Each failed model is listed in `failed_models`. At most one compaction every 3 minutes and 6 an hour (`--force` passes the limits and is still counted).
  Use it on a session that has stopped (a seat at its cap, a killed worker), then `claude --resume <id>`. It refuses a transcript written to in the last `live_guard_sec` (120 s): a running Claude Code keeps the conversation in memory, so a splice there changes nothing until a resume and races the session's next write; for the same reason it is not wired into a PreCompact/Stop hook, and a running session's own `/compact` reads its prefix from that seat's cache, which a summary on another model cannot. Measured on 2026-10-31 (aws-sin, a copy of a finished 15.8 MB session, original untouched): resuming the copy as it was sends 606 messages (6.6 MB) to the API; after `compact`, 11 messages (180 KB), the summary first (a local stand-in server, network cut). Two real Haiku turns on the compacted copy then wrote 78,729 tokens to the cache and read them back on the second turn, which recalled the first turn's reply. `pools.*`, `preserve_buckets`, `evict_buckets`, `target_post_compact_tokens` and `keep_warm.min_remaining_5h_pct` in the TOML are descriptive and not read. Tests: `python3 client/cc-compactor.test.py`.

## Middleware

Each one changes only the requests sent to its own provider.

- `plugins/context-budget` (off on the gateway: `enabled: false` in its options 2026-10-31 20:57 (+08), then `magpie plugin off` at 21:22, which also spares the ~7 ms a request magpie spends handing the body to a hook that only returns): for a provider whose window is named in its `windows` option, slims the Anthropic request sent to that provider when the prompt estimate passes `safetyRatio` of the window less `defaultReserveOutput` (head+tail cuts of older `tool_result` and text blocks, base64 images to a note, pair-safe folding of middle turns), and lowers `max_tokens` only when the reply asked for would not fit. A provider not named in `windows` is left alone, and so is `claude` (`preserveCacheProviders`). `log: true` writes one line per rewritten request (provider, model, estimates, stages; no body text). 1.0.x carried its own windows (zcode 200K, devin 262,144, grok 131,072, any other 200K) and lowered `max_tokens` to 32,768/16,384 per provider; magpie's own context sizes are larger (`magpie model context zcode/GLM-5.3` 1M, `devin/claude-opus-5-5` 1M, `grok/grok-4.7` 256K), and from 10-30 18:37 to 10-31 it held zcode requests under about 182K (8,945 requests, 5 over 200K; 287 of the 851 in the two days before were over 200K), with no window that needed it. The node tests time V8; in magpie's moejs a 515K-token request ran past the 250 ms limit and went out unchanged (10-31 11:44). Its seat strategies (`context-budget/weighted`, `context-budget/ceiling`) are routed by no group or provider; before one is, note that `onUsage` keys its cache telemetry on `row.key`/`row.account`, which magpie's usage rows don't have (`providerAccount`, `providerKeyId`), and `Seat.account` is a boolean, so the warm-cache and `accountsFirst` terms would never apply. Tests: `node --test plugins/context-budget/context-budget.test.mjs`.
- `plugins/kiro-harness`: rewrites Claude Code's identity line into `<harness_instructions>`, because Kiro's own prompt already names the model Kiro. It also drops the billing line, which changes every request and spoils Kiro's prompt cache. Tests: `node --test plugins/kiro-harness/kiro-harness.test.mjs`.
- `plugins/long-off-seats` (not loaded since 2026-10-28, see [Routing groups](#routing-groups); its options still map to the deleted long-* groups, so don't turn it back on as it is) (onRequest, before routing): a request for `claude-opus-5-5`, `claude-fable-5-1`, `claude-sonnet-5-5` or `claude-haiku-5-5` (bare, `group/…` or `[1m]`) estimated at `threshold` tokens or more (200000) goes to `group/long-opus`, `group/long-sonnet` or `group/long-haiku`; a model named with its provider is left as asked.
